# 카페형 게시판 구현 학습 정리

> **학습 주제**: 카페와 게시판의 계층 설계, 게시글 소속 검증, 로그인 후 화면 복귀  
> **분석 범위**: `c35a39f` → `df64777` → `95ecb8d` → `e04a6b9` (2026.09.18~09.20)

## 한눈에 보는 개발 흐름

| 단계 | 커밋 | 구현한 기능 | 핵심 학습 |
|---|---|---|---|
| 1 | `c35a39f` | 카페 CRUD와 화면 | 소유자 권한, 생성 트랜잭션 |
| 2 | `df64777` | 카페별 게시판 CRUD와 화면 | 부모·자식 관계, 권한 설정값 검증 |
| 3 | `95ecb8d` | 게시판별 게시글 연결 | 계층형 URL, 데이터 소속 검증, 목록 필터링 |
| 4 | `e04a6b9` | 로그인 후 이전 화면 복귀 | SavedRequest, 세션 상태, 안전한 리다이렉트 |

```text
카페 (/cafe/{cafeId})
  └─ 카페 게시판 (/cafe/{cafeId}/boards/{cafeBoardId}/...)
       └─ 게시글 (/cafe/{cafeId}/board/{cafeBoardId}/post/{bno})
```

## 1. 카페 CRUD: 기능의 최상위 단위 만들기

**구현**: `CafeController`에서 목록·상세·등록·수정·삭제 요청을 처리하고, `CafeServiceImpl`과 MyBatis Mapper로 데이터를 저장했다. 카페 등록 시 `CAFE`에 카페를 추가한 뒤 `CAFE_MEMBER`에 생성자를 `OWNER`로 등록한다. 두 작업은 `@Transactional`로 묶었다. 등록·수정 화면에는 `@Valid`와 `BindingResult`를 적용했다.

**배운 점**

- 카페와 소유자 회원 관계는 함께 성공하거나 함께 실패해야 하므로 서비스 계층의 트랜잭션이 적절하다.
- 수정·삭제는 화면 버튼 노출 여부와 별개로 서버에서 DB의 소유자를 다시 조회해 `Principal`과 비교해야 한다. 특히 GET 수정 화면뿐 아니라 POST 수정 요청에서도 검사한다.
- 수정 대상 ID는 폼 입력값보다 URL의 `cafeId`를 사용한다. 사용자가 전송한 필드를 그대로 신뢰하지 않는 방식이다.
- 조회·수정·삭제 결과가 없으면 `CafeNotFoundException`으로 처리해 정상 흐름과 오류 흐름을 구분한다.

## 2. 카페 게시판 CRUD: 카페 안에 게시판 배치하기

**구현**: `CAFE_BOARD` 모델과 DTO·Mapper·Service를 추가했다. 게시판에는 유형, 읽기·쓰기 권한 수준, 표시 순서, 상태가 있다. 카페 상세 화면에 해당 카페의 활성 게시판 목록을 보여주고, 소유자만 게시판을 등록·수정·삭제할 수 있게 했다.

**배운 점**

- 게시판 단건 조회와 수정·삭제 SQL에 `CAFE_ID`와 `CAFE_BOARD_ID`를 함께 넣으면 다른 카페의 게시판 ID를 URL에 끼워 넣는 경우를 막을 수 있다.
- 목록은 `STATUS = 'ACTIVE'`로 제한하고 `DISPLAY_ORDER`, ID 순으로 정렬한다. 삭제는 행을 없애지 않고 `STATUS = 'DELETED'`로 바꾸는 소프트 삭제다.
- `GUEST`에게 쓰기 권한을 주지 않는 규칙을 화면 선택지, 컨트롤러 검증, 서비스 검증에 반영했다. 화면을 우회한 요청에도 규칙이 적용된다.
- 게시판 등록·수정의 GET과 POST 모두 카페 소유자를 확인한다.

## 3. 게시판별 게시글 연결: URL과 데이터 범위를 일치시키기

**구현**: 게시글 주소를 `/cafe/{cafeId}/board/{cafeBoardId}/post` 아래로 옮기고 `BOARD.CAFE_BOARD_ID`를 연결했다. 목록 조회와 총 건수 조회에 게시판 ID 조건을 추가해 검색·페이지 이동에서도 해당 게시판의 글만 다룬다.

**배운 점**

- URL이 계층적이어도 데이터가 자동으로 격리되지는 않는다. 게시글 상세·수정·삭제에서 조회한 글의 `cafeBoardId`와 URL의 값을 비교해야 한다.
- 글 등록 시 `cafeBoardId`는 전송된 DTO의 값을 그대로 사용하지 않고, URL로 조회한 게시판 값으로 설정한다. 수정 시에도 글 번호와 작성자, 게시판 ID를 저장된 데이터 기준으로 다시 설정한다.
- MyBatis에서 `cafeBoardId`와 `pageRequest`를 함께 전달하면서 XML의 참조를 `pageRequest.keyword`, `pageRequest.skip`처럼 변경했다. 목록 쿼리와 총 건수 쿼리에 같은 게시판 조건을 넣어야 페이지 수가 맞는다.
- 기존 게시글 링크와 리다이렉트도 새 주소 체계에 맞춰 함께 수정해야 실제 화면 이동이 끊기지 않는다.

## 4. 로그인 후 이전 화면 복귀: 진입 경로별 이동 처리

**구현**: 헤더 로그인에서는 현재 페이지를 `returnUrl`로 전달한다. 댓글 작성·글쓰기 진입은 카페·게시판·글 번호를 세션에 저장한다. 보호된 URL에 직접 접근한 경우에는 Spring Security의 `SavedRequest`를 사용한다. 로그인 성공 핸들러가 이 순서로 목적지를 결정한다.

```text
로그인 성공
  1. 보호된 URL의 SavedRequest가 있으면 해당 URL
  2. 헤더 로그인에서 받은 returnUrl이 있으면 이전 페이지
  3. 댓글·글쓰기용 카페/게시판 정보가 있으면 해당 화면
  4. 없으면 /cafe
```

**배운 점**

- 사용자가 직접 로그인 버튼을 누른 경우 오래된 `SavedRequest`를 제거해 과거 접근 주소가 현재 목적지보다 우선하지 않게 했다.
- 로그인 실패 시 세션의 복귀 정보를 유지해 로그인 화면의 ‘돌아가기’ 링크를 다시 만든다. 성공 후에는 세션 정보를 삭제해 다음 로그인에 재사용되지 않게 한다.
- `returnUrl`은 현재 애플리케이션의 내부 경로인지 검사한다. 외부 URL, `//`, 역슬래시, 줄바꿈, 로그인·로그아웃 및 `WEB-INF` 경로를 거부해 임의 사이트로 이동하는 위험을 줄인다.
- 로그인 처리 POST는 `MemberController`가 아닌 Spring Security가 담당한다. 컨트롤러는 로그인 화면과 복귀 정보 준비를 맡고, 성공 핸들러는 최종 이동을 맡는다.

## 네 커밋을 통해 정리한 설계 원칙

1. **관계는 저장할 때부터 명확히 한다.** 카페 → 게시판 → 게시글의 부모 ID를 모델과 DB에 연결한다.
2. **URL과 DB 소속을 함께 확인한다.** 경로 변수만으로 접근 대상을 신뢰하지 않는다.
3. **권한은 서버에서 다시 검사한다.** 화면 제어는 사용자 경험이고, 최종 판단은 요청 처리 코드가 한다.
4. **한 작업의 여러 DB 변경은 트랜잭션으로 묶는다.** 카페와 소유자 등록이 대표적인 예다.
5. **로그인 전후 상태는 우선순위와 수명을 정한다.** 목적지를 결정한 뒤 세션 정보를 정리한다.

## 회고와 다음 확인 항목

- 네 커밋은 기능 구현 과정을 보여준다. 이 문서는 코드와 diff를 분석한 결과이며, 실행 테스트 결과를 뜻하지 않는다.
- 게시판의 읽기·쓰기 권한 값은 이 시점에 저장·검증되지만, 게시글 요청 전반에 대한 실제 권한 적용은 별도 확인이 필요하다.
- `returnUrl`의 경로 정규화나 인코딩된 특수 문자까지 포함한 우회 사례는 추가 테스트할 가치가 있다.
- 대표 확인 시나리오: 카페 소유자 외 수정·삭제 거부, 다른 카페 게시판 ID 접근 거부, 다른 게시판의 글 ID 접근 거부, 로그인 실패 후 재시도와 성공 후 복귀, 오래된 세션 복귀 정보 제거.

---

**핵심 문장**: 카페형 게시판에서는 화면의 계층 구조를 URL과 데이터 관계에 반영하고, 각 요청에서 소속과 권한을 다시 검증해야 한다. 로그인 복귀 기능도 사용자의 진입 경로에 따라 목적지를 정하고, 사용한 상태를 정리해야 안정적으로 동작한다.
