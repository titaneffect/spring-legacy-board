## 1. 댓글·첨부파일까지 권한 범위 넓히기

게시글 화면에만 읽기·쓰기 권한을 걸어도 댓글 REST API나 첨부파일 URL에 직접 요청하면 데이터에 접근할 수 있다. `958187f`에서는 각 요청의 리소스가 속한 게시글과 게시판을 DB에서 찾아 게시판 권한을 다시 검사했다.

```text
첨부파일 ID → 게시글 ID → 게시판 ID → 카페 ID·읽기 권한
댓글의 게시글 ID → 게시판 ID → 카페 ID·읽기/쓰기 권한
```

- 댓글 목록 조회에는 **읽기 권한**, 댓글 등록·수정·삭제에는 **쓰기 권한**을 적용했다.
- 댓글 수정·삭제는 쓰기 권한에 더해 **원래 댓글 작성자**인지 확인한다. 등록 시 작성자도 요청 본문 대신 로그인 사용자로 설정한다.
- 첨부파일 응답은 실제 파일을 로드하기 전에 읽기 권한을 확인한다. 게시글 화면의 버튼이나 링크를 숨기는 것과 별개로 파일 URL 자체를 보호한다.
- 첨부파일·댓글 API에는 카페 ID가 URL에 직접 포함되지 않으므로, 실제 소속을 게시글과 게시판 관계를 따라 조회한다.

> **핵심**: 권한 정책은 화면 단위가 아니라 데이터에 접근하는 모든 엔드포인트에 적용해야 한다.

## 2. 카페 게시판 탐색 메뉴 개선

기존 사이드바의 고정된 ‘전체글보기’ 링크를 카페의 게시판 목록으로 바꿨다. 게시판 목록·상세·등록·수정 화면과 검증 실패 후 다시 표시되는 화면에도 `cafeBoardList`를 모델에 담았다. 현재 보고 있는 게시판에는 활성 표시를 적용했다.

**학습 포인트**

- JSP 공통 조각을 여러 화면에서 쓸 때는 그 조각이 필요한 데이터가 **모든 화면 경로**에서 전달되어야 한다.
- 성공 화면뿐 아니라 입력 검증 실패로 같은 JSP에 돌아오는 경로도 확인해야 메뉴가 사라지지 않는다.
- 현재 게시판 ID와 메뉴 항목 ID를 비교하면 사용자가 자신의 위치를 쉽게 파악할 수 있다.

## 3. 사용자 입력 출력과 검색 링크 안전하게 다루기

`b719a43`은 검색어·작성자·파일명·댓글 입력값처럼 사용자가 만든 문자열을 JSP에 출력하는 부분을 손봤다. HTML 텍스트나 속성에는 `c:out`, `fn:escapeXml`을 사용하고, 검색·페이지 이동 링크에는 쿼리 파라미터 인코딩을 적용했다.

| 데이터가 놓이는 곳 | 적용한 처리 | 이유 |
|---|---|---|
| HTML 텍스트·속성 | `c:out`, `fn:escapeXml` | `<`, `&`, 따옴표 등이 마크업으로 해석되는 문제 완화 |
| 검색어가 포함된 URL | `UriUtils.encodeQueryParam`, `c:url`·`c:param` | 공백·`&` 등으로 검색 조건이 깨지는 문제 방지 |
| HTML 속성 안의 링크 | URL 구성 후 `fn:escapeXml` | URL의 `&` 등을 속성 문맥에 맞게 출력 |
| JavaScript에서 쓸 사용자 이름 | 이스케이프된 `data-*` 속성에서 읽기 | 사용자 문자열을 JS 문자열 리터럴에 직접 끼워 넣지 않음 |

> **핵심**: URL 인코딩과 HTML 이스케이프는 목적이 다르다. 먼저 URL 파라미터를 올바르게 만들고, 그 URL을 HTML에 출력할 때 다시 해당 문맥에 맞게 처리한다.

## 4. TinyMCE와 안전한 리치 텍스트 출력

`dc41652`에서는 글 등록·수정 화면에 TinyMCE를 붙이고, 본문을 HTML로 표시하도록 바꿨다. HTML을 그대로 출력하면 사용자 입력이 실행될 수 있으므로 `BoardHtmlSanitizer`를 거친 `safeContent`를 상세 화면에 전달한다.

**허용 정책의 주요 내용**

- 일반 서식·블록·표·스타일·링크는 OWASP HTML Sanitizer 정책을 사용한다.
- 유튜브 iframe은 `https://www.youtube.com/embed/{11자리 영상 ID}` 형태만 허용한다. 다른 호스트·포트·사용자 정보·이벤트 속성은 허용하지 않는다.
- 이미지는 `/attachments/{양의 정수}/view` 형태의 로컬 첨부 경로만 허용한다.
- 테스트는 정상 유튜브 주소가 남고, 다른 사이트 주소와 `onload` 속성이 제거되는지 확인한다.

```text
TinyMCE 입력 → 게시글 본문 저장 → 상세 조회
                              → HTML 정제 → safeContent 출력
```

**학습 포인트**

- 리치 텍스트는 태그가 필요하므로 본문 전체를 일반 텍스트처럼 이스케이프할 수 없다. 허용할 HTML과 속성의 범위를 정해 정제해야 한다.
- 첨부 이미지 경로를 허용하더라도 실제 이미지 응답은 앞서 구현한 첨부파일 읽기 권한 검사에 의해 보호된다.
- HTML 정제 정책에는 허용한 URL의 프로토콜·호스트·경로까지 구체적으로 제한하는 편이 안전하다.

## 네 커밋을 관통하는 원칙

1. **하나의 데이터에는 여러 접근 경로가 있다.** 게시글, 댓글 API, 첨부파일 URL을 모두 확인한다.
2. **화면 상태와 서버 권한을 함께 설계한다.** 메뉴·버튼 표시는 안내이고, 요청 처리에서 최종 검사를 한다.
3. **출력 문맥에 맞게 문자열을 처리한다.** HTML, URL, JavaScript는 서로 다른 규칙을 쓴다.
4. **리치 텍스트는 허용 목록으로 정제한다.** 필요한 서식과 미디어만 통과시킨다.
5. **공통 화면 데이터는 오류 경로까지 공급한다.** 검증 실패 화면에서도 탐색 경험을 유지한다.
