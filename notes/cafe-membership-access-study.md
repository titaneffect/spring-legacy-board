# 카페 회원 관리와 게시판 권한 적용 학습 정리

> **분석 커밋**: `0ec0172` → `fab03f9` → `aab1a81` → `69c2a19` → `cb9296c`  
> **핵심 주제**: 카페 회원의 역할·상태 관리와 게시판 읽기·쓰기 권한

## 구현 흐름 한눈에 보기

| 단계 | 커밋 | 구현 내용 | 핵심 학습 |
|---|---|---|---|
| 1 | `0ec0172` | 카페 회원 목록과 관리 화면 | 회원 데이터를 DTO로 전달하고 관리자 UI 구성 |
| 2 | `fab03f9` | 카페 가입, 회원 역할 변경 | OWNER·MANAGER·MEMBER 역할과 서버 권한 검사 |
| 3 | `aab1a81` | 탈퇴와 재가입 | 회원 기록을 유지하며 상태 전이 처리 |
| 4 | `69c2a19` | 강퇴와 강퇴 해제 | BANNED 상태와 운영자 보호 규칙 |
| 5 | `cb9296c` | 게시판 읽기·쓰기 권한 적용 | 회원 역할을 실제 게시글 요청에 연결 |

```text
사용자 ── 카페 회원 기록 ── 역할: OWNER / MANAGER / MEMBER
                         └─ 상태: ACTIVE / WITHDRAWN / BANNED / PENDING

카페 게시판 ── 읽기 기준 / 쓰기 기준
                   ↓
             로그인 여부 + 활성 회원 역할을 검사
```

## 1. 카페 회원 관리 화면

카페 회원 전용 `CafeMemberController`, Service, DTO를 추가하고, 카페별 회원 목록을 관리 화면에 표시했다. 카페 상세·설정 화면에서도 회원 관리로 이동할 수 있도록 UI를 연결했다.

**학습 포인트**

- 카페 회원은 서비스의 조회 결과를 DTO로 변환해 화면에 전달한다. DB 객체와 화면에 필요한 데이터를 구분할 수 있다.
- 관리 기능은 목록만 만드는 것으로 끝나지 않는다. 카페 상세 화면의 진입 링크와 회원 목록 화면의 조작 UI까지 연결해야 사용할 수 있다.

## 2. 카페 가입과 역할 변경

가입 기능은 현재 로그인한 사용자를 카페의 `MEMBER`로 등록한다. 역할 변경은 카페 `OWNER`가 회원을 `MEMBER` 또는 `MANAGER`로 바꾸는 흐름이다. 서비스는 요청자의 역할, 대상 회원의 존재, 변경하려는 역할을 다시 확인한다.

**학습 포인트**

- `Principal`에서 현재 사용자를 얻고, 대상 사용자는 별도 값으로 받는다. 요청자와 대상을 분리해야 권한 판단이 명확해진다.
- 화면에서 OWNER 선택지를 숨기는 것만으로는 부족하다. 서비스가 OWNER로 변경하는 요청과 OWNER 자신의 역할 변경을 거부한다.
- 카페별 역할은 사이트 전체 권한과 범위가 다르다. 같은 사용자가 카페마다 다른 역할을 가질 수 있다.

## 3. 탈퇴와 재가입: 회원 상태 전이

탈퇴 시 회원 기록을 제거하는 대신 `WITHDRAWN`으로 상태를 바꾼다. 재가입할 때는 전체 상태를 조회해 기존 기록이 없으면 INSERT하고, `WITHDRAWN`이면 기존 행을 다시 활성화한다. `ACTIVE`는 중복 가입으로, `BANNED`는 재가입 불가로 처리한다.

| 현재 상태 | 가입 요청 결과 |
|---|---|
| 기록 없음 | 새 MEMBER 등록 |
| ACTIVE | 중복 가입 거부 |
| WITHDRAWN | 기존 기록 재활성화 |
| BANNED | 재가입 거부 |
| PENDING | 승인 대기 안내 |

**학습 포인트**

- 탈퇴와 강퇴는 모두 비활성 상태처럼 보이지만 의미와 재가입 정책이 다르다. 상태를 따로 두어야 정책을 정확히 표현할 수 있다.
- 카페 소유자는 탈퇴할 수 없도록 서비스에서 막아, 소유자 없는 카페가 생기는 흐름을 방지한다.
- `ACTIVE` 회원만 조회하는 메서드와 모든 상태를 조회하는 메서드를 구분해야 재가입이나 강퇴 해제를 처리할 수 있다.

## 4. 강퇴와 상태 관리

강퇴와 해제는 카페 OWNER만 수행한다. 강퇴 대상이 현재 카페 회원인지 확인하고, OWNER는 강퇴할 수 없게 했다. 해제할 때는 대상이 실제 `BANNED` 상태인지 검사한다.

**학습 포인트**

- 관리자 작업은 요청자 권한과 대상 상태를 모두 검증해야 한다.
- `BANNED`를 별도 상태로 유지하면 강퇴 이력을 반영하면서 재가입 차단과 해제 기능을 구현할 수 있다.
- 상태 변경 SQL의 영향 행 수를 확인해 존재하지 않는 대상이나 예상과 다른 상태의 변경을 성공으로 처리하지 않는다.

## 5. 게시판 읽기·쓰기 권한 적용

`CafeBoardAccessService`가 카페 회원의 역할을 게시판의 요구 권한과 비교한다. `GUEST`는 로그인하지 않아도 접근할 수 있고, `MEMBER`는 활성 카페 회원, `MANAGER`는 매니저 또는 소유자, `OWNER`는 소유자만 허용한다. `BoardController`는 목록·상세에서 읽기 권한을, 등록·수정·삭제 요청에서 쓰기 권한을 확인한다.

| 게시판 요구 수준 | 접근 가능한 사용자 |
|---|---|
| GUEST | 누구나 |
| MEMBER | 활성 카페 회원 전체 |
| MANAGER | 매니저, 소유자 |
| OWNER | 소유자 |

**학습 포인트**

- 게시판에 저장해 둔 `readRole`·`writeRole` 값은 실제 요청에서 검사할 때 비로소 권한 정책이 된다.
- 글쓰기 화면 GET뿐 아니라 등록 POST도 검사한다. 수정·삭제에서는 게시판 쓰기 권한과 글 작성자 여부를 모두 확인한다.
- `canWrite`를 화면에 전달해 버튼 표시를 조절하지만, 서버의 `AccessDeniedException` 검사가 최종 접근 통제다.
- 게시글의 `cafeBoardId`와 URL의 게시판 ID 비교도 계속 유지해, 다른 게시판의 글 번호를 넣는 요청을 차단한다.

## 다섯 커밋을 관통하는 설계 원칙

1. **역할과 상태를 분리한다.** 역할은 무엇을 할 수 있는지, 상태는 현재 카페 회원으로 활동할 수 있는지를 나타낸다.
2. **상태 변경을 전이 규칙으로 설계한다.** 탈퇴 후 재가입과 강퇴 후 해제는 서로 다른 흐름이다.
3. **요청자와 대상을 따로 검증한다.** 회원 관리 기능에서는 둘의 역할과 상태가 모두 중요하다.
4. **권한 설정과 권한 적용을 연결한다.** 저장된 읽기·쓰기 기준을 게시글 요청마다 검사한다.
5. **UI와 서버 검사를 함께 구현한다.** 버튼 노출은 사용성을 높이고, 서버 검사는 우회 요청을 막는다.

## 제출용 회고

> 카페 회원 관리 기능을 구현하며 회원의 역할과 상태를 별개로 다뤄야 한다는 점을 배웠다. 가입·탈퇴·재가입·강퇴는 단순 CRUD보다 상태 전이 규칙이 중요했다. 이후 게시판에 설정된 읽기·쓰기 권한을 실제 게시글 요청에 적용하면서, 화면의 버튼 표시와 서버의 접근 검사는 함께 구현해야 한다는 점을 확인했다.

**주요 키워드**: `카페 회원 관리` · `역할 기반 접근 제어` · `회원 상태 전이` · `소프트 삭제` · `서버 측 권한 검사` · `Spring Security`

**검증 범위**: 이 문서는 지정한 커밋의 코드와 변경 내역을 분석한 학습 정리다. 실행 테스트 결과나 실제 운영 중 발생한 오류를 주장하지 않는다.
